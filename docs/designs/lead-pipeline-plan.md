## Problem statement

Salesmen visit shop to shop. A guarded owner gets the Engagement Form: 9 questions, asked
conversationally, written to collect what we need for nurturing. An owner who talks gets Pain Discovery
and a loan pitch. Some owners then say "Interested", and today nothing checks whether we can actually
serve them. "Interested" is also invisible to managers (it only counts as `active`). Follow-ups,
objections and the time between qualification and login are not tracked either.

## Premise check (results of the review)

| # | Premise in the plan | Verdict | Why |
|---|---|---|---|
| 1 | Engagement Form stays as is | **Agree** | The questions are deliberate: E7 is asked in third person so the owner reveals his own problem, and E3/E4/E5 show *when* he buys stock. Do not trim it. |
| 2 | Interested becomes a stage | **Agree** | It is a real customer milestone, and managers cannot see it today. |
| 3 | ROI becomes a tool, not a stage | **Agree, but change how** | The plan moved roi_shown leads *backward* to rank 30 or 20. That breaks the forward-only rule (007) and needs the guard switched off. See fix F1. |
| 4 | Negotiation stage | **Change** | A stage nobody can verify gets marked to look busy. In DSA lending the rate is set by the lender, so the real work after qualification is collecting documents. See fix F2. |

| 6 | Hot / Warm / Cold stored by a DB trigger | **Change** | Temperature depends on time (decay, season window), and a trigger only fires on new events, so stored values go stale. See fix F3. |
| 7 | Auto-create a revisit reminder for every Engagement lead | **Change** | Hundreds of future reminders will flood the salesman's reminder list. See fix F4. |

## Fixes to the plan

**F1. Put the new stages *above* the retired ROI rank, so nothing ever moves backward.**
```
new 0 → visited 10 → pain_identified 20 → [roi_shown 50, retired] → interested 55 → qualified 60 → documents 70 → login_started 80
```
A lead sitting at roi_shown (saw ROI, never said yes) is correctly *between* Pain and Interested.
It moves forward to Interested normally. No backfill and no disabled guard: it is the same
retirement pattern as approved/disbursed. The migration only adds rows to `stage_defs` and sets
roi_shown `is_live = false`.

**F2. Replace "Negotiation" with a "Documents" stage that has evidence.**
- **Enters** when the first document is ticked: PAN, Aadhaar, 6-month bank statement, GST/Udyam,
  shop photo/rent agreement, co-applicant KYC.
- **Shows** "4 of 6 documents" on the lead card.
- **Manager gets the same visibility** that "Negotiation" was meant to give, but the number cannot
  be faked by a single tap.
- Objections are still logged on these leads as tags.

**F3. Compute temperature in a view, not stored by a trigger.**
- A `lead_temperature` view (or SQL function) reads the latest events plus `now()`.
- Decay and the season window are always current, nothing goes stale, and there is no cron job.
- The admin console can still sort and filter by it.
- The unused `intent_level` column (nothing in the app writes it; it defaults to 'low') is left
  untouched, then dropped later.

**F4. Show revisits as a computed list, not reminder rows.**
A "Revisit this week" list is computed from peak months − prep time. A real reminder is created
only when the salesman taps "Plan visit". The reminder list stays for things a person actually
committed to.

## Approaches

**A. Wedge (recommended first)** · S effort (human ~3-4 days / CC ~1-2 hours) · Low risk
1. Migration: add `interested 55` + `qualified 60`, retire roi_shown (F1). The trigger maps the
   `customer_response = interested` event to Interested.
2. Qualification block on Interested: extends the existing Loan Requirement block with the 7 new
   questions and the 6 check results (Money, Use, Timeline, Authority, Need, Trust). Saved as a
   `qualification_done` event, which moves the lead to Qualified.
3. Not Qualified with a reason and an optional revisit date (uses the existing `not_qualified`
   status from 009).
4. A follow-up reason chip (from the objection list) is required when a follow-up is set.
5. A checklist on the lead card (Engagement / Pain / ROI / Qualification) and a "Pain pending" badge.
6. One shared temperature function replaces `deriveIntent`, `isHot` and `intentScore`.

**B. Full plan with fixes F1-F4** · L effort (human ~3 weeks / CC ~1 day) · Medium risk
Wedge + Documents stage + objection tags with scripts + temperature view + Revisit list + admin
funnel and filters.

**C. Lateral: a "Next Action" queue instead of temperature labels** · M effort · Medium risk
Every lead carries one next action and a due date ("meet the father Sunday", "collect bank
statement", "revisit before Diwali buying"). The salesman's home screen is today's actions. The
manager sees overdue actions per salesman. Temperature becomes a sort key, not the main thing.
This targets the real goal (salesmen doing the right thing today) more directly than labels do.

**Recommendation: A now, then B in phases. Borrow C's idea** by making the lead card show
"next action" next to the temperature.

## Section 1: Architecture

```
 S_Workspace (Interested ▸ Qualification form) ──insert──► events ──AFTER INSERT──┬─► apply_stage_from_event (007, extended)
 S_PainDiscovery / S_CustomerForm ───────────insert──► events                     └─► apply_status_from_event (009)
                                                          │
 Dashboard / Workspace / Admin ◄──select── lead_temperature VIEW (security_invoker) ◄─┘ reads latest events + now()
```

**Stage changes (one-way, enforced by `keep_stage_forward`):**
```
pain_identified(20) ─► [roi_shown 50, retired] ─► interested(55) ─► qualified(60) ─► documents(70) ─► login_started(80)
Lower-rank events are recorded, but the stage does not move. A closed status blocks advancing.
```

**Findings:**
- **A1 (Medium). Trigger order conflict on reactivation.** Both triggers are AFTER INSERT on
  `events` and fire in alphabetical order, so `events_apply_stage` runs before `events_apply_status`.
  - When a *dormant* lead says Interested, the stage trigger runs first, sees a closed status and
    skips. Then the status trigger reactivates the lead.
  - **Result:** the lead is active again but still at its old stage.
  - **Fix:** in the stage trigger, treat `customer_response = interested` as reactivating before the
    closed-status check, or merge the two triggers for this event.
  - **Test:** dormant lead + interested event ends at interested(55) with status active.
- **A2 (Low). Interested must be matched on the response, not the event type.** The trigger has to
  match `event_type = 'customer_response' AND data->>'response' = 'interested'`. Thinking and Nahi use
  the same event type and must not move the stage.
- **Rollback:** the migration only adds stage rows and flips `roi_shown.is_live`. Rolling back means
  setting `is_live` back and deleting the 3 new rows, but only if no lead has reached them. After
  that point it is forward-only, and a reverse fix needs the guard disabled. Rollback time is about
  5 minutes before adoption.

## Qualification rules (final, with D1 applied)

Inputs: total monthly family income (used for the Money check; the existing "Total monthly family income" field), monthly business income (information only), existing EMI, new EMI (from the ROI tool or
estimated from amount + tenure), loan amount, use of funds, needed-by, decision maker, co-applicant,
shop age (years), past bounce/default (yes/no), property (yes/no + type), consent tick.

| Check | Pass ✅ | Gap 🟡 | Fail ❌ |
|---|---|---|---|
| **Money** | (existing EMI + new EMI) ÷ total monthly family income ≤ 70% | Family income not given | > 70% |
| **Use** | Stock / supplier payment / shop upgrade / machine | Mixed or "other" | Repay another loan / home expense |
| **Timeline** | Needed within 15 days | 16-45 days | > 45 days (→ nurture + reminder at that date) |
| **Authority** | Owner decides + co-applicant available | Needs family consult | Talker is not the owner and the owner can't be met |
| **Need** | Pain Discovery done AND loan ≤ 1.5 × indicative ticket | No Pain Discovery yet, or loan 1.5-2.5× | Loan > 2.5× indicative ticket |
| **Trust** | Shop age ≥ 1 year AND no past default | — | Shop age < 1 year (temporary → nurture, revisit at 1 year) · past default (permanent → not_qualified) |

Property is recorded as information (it opens up secured-loan options) and is not a check.
No consent tick → the form cannot be saved.

**Result:**
- **Qualified:** every check Pass. Stage → qualified (60).
- **Gaps only:** stage stays at interested; the card shows the first gap as the next action.
- **Any Fail:** the Not Qualified sheet opens. It suggests nurture or not_qualified per D2.

**Temperature:**
- 🔥 **Hot:** Qualified + Timeline Pass (within 15 days).
- 🟡 **Warm:** Pain done with a money-solvable problem, OR Interested with gaps, OR Qualified but
  needed after 15 days.
- ❄️ **Cold:** engagement only, or "no need now".

Decay: no event for 15 days → down one level; 30 days → Cold.

## 1. Architecture

Findings:
- **[P1, confidence 9/10, source 007/009] E2. Trigger order.** Postgres fires same-timing triggers
  by name, so today `events_apply_stage` runs before `events_apply_status`. A dormant lead that says
  Interested is reactivated, but its stage does not advance.
  Fix: rename the triggers `events_10_status` and `events_20_stage` (drop and recreate). This is

- **[P1, 9/10, 009 line 73-79] E7. D2 cannot work under today's rules.** Sales may only set `lost`
  or `not_qualified` through `status_changed`. Nurture is reachable only via a "Nahi" response.

- **[P1, 9/10, plan D3] E3. The DB must decide "qualified".** `stage_defs` only knows `min_photos`
  as evidence.

    `qualification_rules`.
  - A BEFORE INSERT trigger on `qualification_done` overwrites `data.checks` with the server result,
    so the client's result is ignored.
  - The stage trigger advances to qualified only when every check is Pass. Otherwise the event is
    stored and the stage stays put.
- **[P1, 8/10, 007 `event_type UNIQUE`] E4. Interested needs a data match.** Add
  `stage_defs.match_data jsonb`, and have the trigger require `NEW.data @> d.match_data` when it is
  set. Interested = `customer_response` + `{"response":"interested"}`. Thinking and Nahi then fall

## Pass 6: Phone use & accessibility: 3/10 → 8/10 if DR8 is approved

**DR8.**
- **Touch targets:** at least 44px (`min-h-[44px]`). Today's chips use `py-2`, which is about
  34px. Thumbs miss them while standing.
- **Save placement:** sticky at the bottom inside the card's scroll area, in the thumb zone.
- **Amounts:** `inputMode="numeric"`, a ₹ prefix, Indian grouping while typing ("5,00,000"), and a
  "= 5 lakh" echo, so a missing zero is caught on the spot.
- **Contrast:** labels move from `text-slate-400` (about 2.6:1, unreadable in sunlight) to
  `text-slate-600`. Results never rely on colour alone (symbol + word).
- **Screen readers:** the result row is `aria-live="polite"`. Each chip is a real `<button>` with
  `aria-pressed`.
